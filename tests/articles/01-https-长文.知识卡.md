《HTTPS 到底安全在哪里》共提炼 7 张知识卡。

## 卡片 1｜HTTPS 本质是 HTTP over TLS

- **核心知识**：HTTPS 即 HTTP over TLS，在 HTTP 和 TCP 之间插入一层 TLS 协议，为传输提供加密、身份认证和完整性保护。
- **简明解释**：不加密的 HTTP 传输像明信片，任何中间节点都能看到甚至篡改内容。TLS 层把窃听、冒充、篡改三类风险一起解决，浏览器的小锁图标只是这些机制正常工作的外在表现。
- **例子/自测**：例子：原文类比——未加保护的传输"像明信片一样在邮路上裸奔"。

## 卡片 2｜会话密钥用对称加密保障速度

- **核心知识**：TLS 用对称加密的会话密钥加密实际数据，加解密速度快、适合大量数据，但前提是双方先安全地拿到同一个密钥。
- **简明解释**：对称加密的短板正在于密钥分发：第一次通信的信道本身不安全，不能指望直接把密钥明着发过去。因此 TLS 把"数据加密"和"密钥分发"拆成两个问题分别解决。
- **例子/自测**：自测问题：为什么不用非对称加密直接加密全部通信内容？答案要点：非对称加密加解密开销大、速度慢，不适合加密大量数据，只适合用来交换密钥。

## 卡片 3｜非对称加密解决密钥分发问题

- **核心知识**：服务器持公钥/私钥对：客户端用公钥加密预主密钥发给服务器，只有持私钥的服务器能解密，双方再各自推导出会话密钥。
- **简明解释**：公钥可以公开，私钥只有服务器保管。这样即使首次通信的信道不安全，攻击者也拿不到最终使用的会话密钥。
- **例子/自测**：自测问题：预主密钥在密钥交换中起什么作用？答案要点：客户端用服务器公钥加密预主密钥传给服务器，双方各自从它推导出会话密钥。

## 卡片 4｜ECDHE 密钥交换提供前向保密

- **核心知识**：现代 TLS 常用 ECDHE 密钥交换（椭圆曲线 Diffie-Hellman）：每个会话的密钥临时生成、用完即弃，即使服务器私钥日后泄露也无法解密过去录制的流量，这就是前向保密。
- **简明解释**：前向保密把单次密钥泄露的损失限制在单个会话内。TLS 1.3 干脆只保留 ECDHE 系列密钥交换，强制获得这一特性。
- **例子/自测**：例子：TLS 1.3 中只保留 ECDHE 系列密钥交换，正是为了强制支持前向保密。

## 卡片 5｜CA 签发数字证书完成身份认证

- **核心知识**：数字证书由受信任的证书颁发机构（CA）签发，把服务器域名与公钥绑定并附上 CA 签名；客户端验证签名来源、域名匹配和有效期来确认服务器身份。
- **简明解释**：加密只解决"别人看不懂"，身份认证解决"对面是不是真的服务器"。浏览器内置受信任的 CA 列表，据此验证证书链，识别中间人冒充。
- **例子/自测**：自测问题：客户端验证证书时主要检查哪三项？答案要点：是否由受信任 CA 签发（签名有效）、域名是否匹配、证书是否过期。

## 卡片 6｜跳过证书校验等于向中间人敞开

- **核心知识**：证书绑定的是公钥而非会话密钥；若跳过证书校验（如点击"继续访问不安全的网站"），加密依然存在，但通信对象可能是中间人，安全性完全失效。
- **简明解释**：证书体系防的是中间人冒充。放弃校验就放弃了身份认证这根支柱，此时"加密"反而制造安全错觉。
- **例子/自测**：例子：用户点了"继续访问不安全的网站"后，可能正与中间人进行加密通信。

## 卡片 7｜消息认证码 MAC 防止数据被篡改

- **核心知识**：TLS 每条记录附带基于会话密钥计算的消息认证码（MAC），接收方可验证数据是否被篡改；加密保证"看不懂"，MAC 保证"没改过"。
- **简明解释**：若只有加密而无完整性保护，攻击者虽看不到明文，仍可能乱改密文造成破坏。两者结合才构成完整的传输安全。
- **例子/自测**：自测问题：TLS 中"加密"和"MAC"分别防御什么？答案要点：加密防窃听（机密性），MAC 防篡改（完整性）。
