# HTTPS 到底安全在哪里

互联网上传输的数据如果不加保护，就像明信片一样在邮路上裸奔：任何一个中间节点都能看到内容，甚至篡改内容。HTTPS 就是为了解决这个问题而生的。很多人只知道"网址带小锁就是安全的"，但它的安全机制远不止一个小锁图标。

## 加密：从明文到密文

HTTPS 的全称是 HTTP over TLS，也就是在 HTTP 和 TCP 之间加了一层 TLS 协议。TLS 的核心作用是加密：客户端和服务器协商出一个只有双方知道的会话密钥，之后所有数据都用这个密钥加密传输。即使攻击者在链路上截获了数据包，看到的也只是密文。

这里的关键在于"会话密钥"。会话密钥是对称加密密钥，加解密速度快，适合加密大量数据。但对称加密有一个前提：双方得先安全地拿到同一个密钥。这在开放的互联网上并不容易，因为第一次通信的信道本身就不安全。

## 密钥交换：让窃听者拿不到密钥

TLS 使用非对称加密来解决密钥分发问题。服务器持有一对密钥：公钥和私钥。公钥是公开的，任何人都能拿到；私钥只有服务器自己保管。客户端用公钥加密一个预主密钥发给服务器，只有持有私钥的服务器能解密。双方再各自从预主密钥推导出会话密钥。

现代 TLS 更常用的是 ECDHE 密钥交换，它基于椭圆曲线 Diffie-Hellman 算法。ECDHE 的优点是支持前向保密：即使服务器的私钥日后泄露，攻击者也无法解密过去录制的流量，因为每个会话的密钥都是临时生成的，用完即弃。这是 TLS 1.3 中干脆只保留 ECDHE 系列密钥交换的重要原因。

## 身份认证：证明"对面是服务器本人"

加密解决了"别人看不懂"的问题，但还有一个问题：你怎么知道对面就是真正的服务器，而不是中间人冒充的？这就需要身份认证，而身份认证依赖数字证书。

数字证书由受信任的证书颁发机构（CA）签发，里面包含了服务器的域名、公钥和 CA 的数字签名。客户端（浏览器）内置了信任的 CA 列表，收到证书后会验证签名是否由受信任的 CA 签发、域名是否匹配、证书是否过期。全部通过，才认为服务器身份可信。

这里有一个容易被忽略的细节：证书里装的是公钥，不是会话密钥。证书的作用是把公钥和域名绑定，解决"公钥属于谁"的问题。如果跳过证书校验，比如用户点了"继续访问不安全的网站"，那么加密虽然还在，但你可能在和中间人加密通信，安全性完全破防。

## 完整性保护

TLS 还提供完整性保护。每条记录都带有基于会话密钥计算的消息认证码（MAC），接收方可以验证数据在传输过程中是否被篡改。加密保证"看不懂"，MAC 保证"没改过"，两者合起来才构成传输安全。

## 总结

所以 HTTPS 的安全建立在三根支柱上：加密让窃听者看不懂，密钥交换（尤其是支持前向保密的 ECDHE）让密钥不落敌手，证书体系证明服务器身份，完整性校验防止数据被篡改。小锁图标只是这些机制全部正常工作的外在表现。
